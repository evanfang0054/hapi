# 2026-04-11 安卓 PWA 系统通知扩展设计

## 背景

当前仓库已经具备完整的 Web Push 基础设施：`web/src/hooks/usePushNotifications.ts` 已支持通知权限申请与推送订阅，`web/src/sw.ts` 已支持 `push` 与 `notificationclick` 事件处理，`hub/src/web/routes/push.ts` 与 `hub/src/push/pushService.ts` 已具备订阅保存与推送下发能力。

但现有“任务结束提醒”主要还是 H5 内部横栏通知体验。用户希望在 **不改变当前通知触发语义** 的前提下，把这套提醒能力扩展到安卓手机系统通知，尤其覆盖 Android Chrome / 已安装 PWA / 页面不在前台 / 锁屏等场景，使通知能够真正离开 H5 页面，在系统层提醒用户。

本次设计的目标不是重做通知体系，而是把 **当前 H5 内部通知** 扩展为 **前台站内横栏 + 后台安卓系统通知** 的双通道通知能力。

## 已确认约束

- 保留当前“什么时候提醒、提醒什么”的通知语义，不重新定义产品规则
- 保留现有 H5 内横栏通知体验，不做替换，只做扩展
- 安卓系统通知应复用现有 Web Push / Service Worker / hub push 链路
- 采用双保险策略：前台保留 H5 横栏，后台通过系统通知补充提醒
- 必须考虑前台、后台、已安装 PWA、网页不在前台、锁屏等安卓场景
- 必须设计去重策略，避免 H5 横栏与系统通知重复轰炸
- 必须补充测试方案，确保具备可交付质量
- 保持 KISS，不新增第三方推送平台、原生 Android App、FCM 专用通道或新的后端服务

## 设计目标

### 1. 扩展而不是替换

沿用现有通知事件语义与前端横栏体验，不推翻当前实现，不重建通知中心。

### 2. 安卓系统可感知

当用户不在当前 H5 前台时，任务结束等已有通知事件应能通过系统通知提醒到安卓手机，包括安装为 PWA 的场景。

### 3. 避免重复提醒

同一事件不能既弹横栏又弹系统通知，或者反复重复发送。通知展示必须有明确分流和去重规则。

### 4. 点击可回到正确上下文

用户点击系统通知后，应能打开或聚焦 HAPI 的 PWA / 浏览器窗口，并跳转到对应 session 或相关页面。

### 5. 可验证、可交付

设计必须包含单元测试、Service Worker 测试、hub 侧测试与真实安卓路径验证，确保不是“理论可行”，而是可以直接交付使用。

## 总体方案

采用 **复用现有 Web Push 基础设施的双通道方案**。

核心思路是：

- 继续以当前 H5 横栏通知的事件语义为准
- 将这类事件收口为统一通知事件对象
- 在前端根据页面可见性、当前活跃 session、用户所处上下文决定展示方式
- 前台场景只显示 H5 横栏
- 后台或不在相关上下文时，通过 hub 推送到 Service Worker，再由安卓系统通知展示

这不是新建一套通知系统，而是把“通知何时触发”与“通知如何展示”解耦：

- **事件源负责判断要不要通知**
- **协调层负责选择 H5 横栏还是系统通知**
- **hub 负责 push 下发**
- **service worker 负责系统展示与点击回跳**

## 方案对比

### 方案 A（推荐）：复用现有 Web Push，增加前后台分流与去重

- 保留当前 H5 横栏通知
- 收口同一通知事件到统一出口
- 前台显示横栏，后台发系统通知
- 使用现有 push 订阅与 service worker 能力

**优点**：改动最小、风险最低、最符合当前代码结构与用户诉求。

**缺点**：需要准确定位当前横栏通知事件源，并补足前后台分流与去重判断。

### 方案 B：统一改成全量系统通知，再由前端决定是否补横栏

- 所有通知都先走系统通知链路
- 前端额外决定要不要显示横栏

**优点**：理论上通知出口更统一。

**缺点**：更容易造成双提醒，且会让现有 H5 通知逻辑变绕，不符合最小改动原则。

### 方案 C：新增一套系统通知专用通道

- 保留横栏逻辑完全不动
- 单独新增“安卓系统通知专线”

**优点**：对旧逻辑侵入低。

**缺点**：双系统长期容易漂移，维护成本高，违背 KISS。

## 推荐方案

采用 **方案 A**。

理由：仓库已具备较完整的 push 基础设施，本次需求本质上不是新通知类型，而是把当前已有通知的展示能力从 H5 页面内扩展到安卓系统层。方案 A 能做到：

- 保留当前触发语义
- 扩展到安卓系统通知
- 减少改动范围
- 支持前台横栏 + 后台系统通知
- 容易做去重与回滚

## 架构与职责边界

建议拆成 4 层职责：

### 1. 通知事件源

负责判定“当前是否该提醒用户”。

这里继续复用现有横栏通知的事件来源，不改业务语义。该层只产生统一通知事件对象，不直接决定显示横栏还是系统通知。

### 2. Web 通知协调层

位于 `web` 侧，负责：

- 判断页面是否可见
- 判断当前是否处于前台
- 判断用户当前是否正在相关 session / 页面
- 决定当前设备是否只显示 H5 横栏，还是应该进入系统通知链路
- 做前台消费与去重控制

这是本次最关键的新逻辑层。

### 3. Hub Push 分发层

复用现有 `hub` 推送能力，负责：

- 接收需发送系统通知的统一通知事件
- 将事件映射为标准 push payload
- 根据 namespace 找到订阅设备
- 通过现有 `PushService` 下发 Web Push

### 4. Service Worker 展示层

复用 `web/src/sw.ts`，负责：

- 接收 push 事件
- 使用 `showNotification` 展示安卓系统通知
- 根据 payload 中的 URL / session 信息在 `notificationclick` 时打开或聚焦 PWA 窗口

## 数据流

```text
现有“该通知了”的事件
  -> 统一通知事件对象
  -> Web 通知协调层
     -> 前台且正在相关上下文：显示 H5 横栏
     -> 其他情况：调用 hub push 分发
        -> Service Worker 接收 push
        -> 安卓系统通知展示
        -> 点击通知后打开/聚焦 PWA 并跳转到目标 session
```

这条数据流的关键点是：

- 同一通知事件只有一个语义来源
- 展示渠道由上下文决定
- push 只在真正需要系统提醒时使用

## 前后台分流规则

### 仅显示 H5 横栏

满足以下条件时，仅显示当前站内横栏通知：

- 页面当前可见
- H5 / PWA 当前在前台
- 用户当前处于相关 session 或足够接近该通知上下文

### 发送系统通知

只要满足任一条件，即应发送系统通知：

- 页面不可见
- 浏览器 / PWA 位于后台
- 设备锁屏
- 用户当前不在相关 session 页面
- 页面被挂起，但 Service Worker 仍可接收 push

这意味着分流不是“网页开着就不推”，而是“**只有当前就在看这个上下文时，才抑制系统通知**”。

这样更符合真实使用场景：即使 H5 仍开着，但如果用户已经切走、锁屏或在看别的 session，这个任务结束提醒仍然应该通过系统通知抵达。

## 通知数据模型

基于现有 `PushPayload` 结构，通知对象保持最小必要字段：

- `title`
- `body`
- `tag`
- `data.type`
- `data.sessionId`
- `data.url`
- 可选稳定事件 id（若现有事件源中能直接拿到）

不额外设计复杂协议，优先复用当前 `web/src/sw.ts` 与 `hub/src/push/pushService.ts` 已支持的 payload 结构。

## 去重策略

本次必须实现三层去重。

### 1. 事件级唯一标识

同一通知事件需要生成稳定 key，建议基于：

- `type`
- `sessionId`
- 与该次完成事件相关的唯一标识（如消息 id、run id、completion id）

该 key 用于前端协调层判断当前事件是否已在本地消费过。

### 2. 系统通知 `tag` 合并

Service Worker 中调用 `showNotification` 时使用稳定 `tag`：

- 同类通知可按 session 粒度或事件粒度覆盖
- 避免同一 session 在短时间内堆积大量重复通知

### 3. 前台消费抑制

如果当前设备已经在前台展示过该事件对应的 H5 横栏，则本设备不应再收到同一事件的系统通知。

目标是避免用户“正看着页面，还被系统再炸一次”。

## 点击通知行为

系统通知点击后的目标行为：

1. 优先查找已有的 HAPI 浏览器 / PWA 窗口
2. 若已有窗口，则聚焦该窗口
3. 若无窗口，则打开目标 URL
4. 落点应直接进入对应 session 页面
5. 必要时可通过 URL 参数携带事件上下文，便于后续页面高亮或定位

当前 `web/src/sw.ts` 已有 `notificationclick` 基础逻辑，本次只需要扩展为更准确的会话跳转与窗口复用策略。

- 安卓 Chrome 中打开 H5，授权通知后，任务结束能收到系统通知
- 安卓已安装 PWA，切后台后，任务结束能收到系统通知
- 锁屏状态下能收到系统通知

- 取消订阅后，不再收到系统通知

## 风险与应对

### 风险 1：当前横栏通知事件源分散

如果当前横栏通知不是从统一通知中心发出，而是零散分布在不同 UI 模块里，则会导致系统通知扩展时触发不一致。

**应对**：先做轻量收口，统一通知出口，但不借机做大规模重构。

### 风险 2：前后台判断不准确

安卓浏览器、已安装 PWA、不同容器下的可见性与前台行为可能存在差异。

**应对**：采用保守规则，并以真机验证为准，不依赖单一浏览器假设。

### 风险 3：重复通知

如果未做事件级去重与 `tag` 合并，用户很容易在一次任务结束时同时看到横栏与系统通知。

**应对**：事件 key + notification tag + 前台抑制三层去重一起上。

## 回滚策略

本次改动属于增强型能力，可局部回退：

- 若系统通知分流存在问题，可只关闭系统通知路径，保留现有 H5 横栏通知
- 若 `notificationclick` 行为不稳定，可先降级为打开默认入口页面
- 若订阅链路在部分设备不稳定，不影响 H5 内部通知继续工作

因此本方案风险可控，不会破坏现有通知主流程。

## 最终结论

本次需求最合适的落地方式，是在现有 H5 横栏通知语义不变的前提下，复用仓库已有的 Web Push 基础设施，补上前后台分流、事件去重和系统通知点击回跳，让安卓用户在 PWA / 浏览器 / 后台 / 锁屏场景中都能接收到任务结束提醒。

该方案满足：

- 最小改动
- 保留现有通知行为
- 安卓系统层可感知
- 不重复轰炸
- 可测试、可回滚、可交付
